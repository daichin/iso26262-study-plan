總覽

ISO 26262-8 不是「軟體怎麼寫」，而是「整個安全生命週期共用的流程骨架」。這些流程平常感覺像行政作業，但它們存在的理由都很具體：讓每一個決定都能被追溯、讓工具鏈本身不會變成安全的破口。

換個角度看會更清楚：Part 3 到 Part 7 是「照時間軸走一遍」的開發階段，從概念、系統、硬體、軟體一路到量產與維修。但有些事情不屬於任何單一階段，而是每個階段都要做同一套——需求怎麼寫才算合格、產出物怎麼版本控管、改東西前要先分析什麼、用的工具憑什麼可以信任。這些橫向共用的規則被集中放進 Part 8，避免在每個 Part 裡重複寫一次。

Part 8 涵蓋哪些主題

你不需要全部精讀，但知道它管到哪些事，之後被問到「這個要求出自哪裡」時才找得到位置：

  • 安全需求的規格與管理——需求要具備哪些屬性、怎麼維持追溯性。很多人以為這在 Part 6，其實規則的本體在這裡。
  • 組態管理與變更管理——產出物怎麼識別、版本化、變更前要做什麼。
  • 驗證——walkthrough、review、inspection 等方法的定義與適用時機。
  • 文件管理——每份文件的目的、讀者與追溯關係。
  • 軟體工具的使用信心（TCL）——編譯器、靜態分析器、測試框架要不要鑑定。
  • 軟體元件鑑定——重用非依標準開發的既有元件時要補什麼證據。
  • 硬體元件評估、既有經驗論證（proven in use）、與非 ISO 26262 範疇的應用介接。

Part 8 和 Part 6 的分工

簡單記法是：Part 6 定義「軟體要做什麼」，Part 8 定義「怎麼做才算數」。Part 6 告訴你單元驗證要達到什麼覆蓋率、架構設計要遵守哪些原則；Part 8 告訴你這些活動的產出物要怎麼版本控管、審查要多正式、以及你用來達成這些活動的工具本身可不可信。

兩者的交界處常常是爭議來源。舉例來說，「這份單元測試報告算不算數」這個問題，答案同時牽涉 Part 6（測試方法對不對）和 Part 8（產生報告的測試工具有沒有經過鑑定、報告有沒有被納入組態管理）。任何一邊沒過，這份證據在 safety case 裡就站不住。

為什麼軟韌體工程師要懂這部分

Part 6（軟體開發）定義「要做什麼」，Part 8 定義「怎麼做才算數」。你交付的程式碼要進安全案例（safety case），走的就是 Part 8 的組態管理、變更管理與驗證規則。

更直接的影響是：專案為什麼鎖住編譯器版本不給你升、為什麼改一行都要開變更單、為什麼你想用的那個開源函式庫被打回票——這些讓人不耐煩的限制，源頭幾乎都在這一章。理解了理由，至少可以判斷什麼時候該據理力爭、什麼時候該乖乖照做。

1組態與變更管理

Configuration management（組態管理）要求每一份會影響安全的產出物——原始碼、需求文件、測試案例、工具版本——都要能被唯一識別、版本化、並且可以重現。這也是為什麼安全專案對「這次建置用的到底是哪個 commit、哪個編譯器版本」要求得比一般專案嚴格得多。

要納管的東西比你想的多

很多團隊第一次做的時候，只把 Git 上的原始碼當成組態項目，結果稽核時被問倒。實際上凡是「換掉之後可能讓產出行為不同」的東西都要納管：

類別具體項目漏掉會怎樣
開發產出物需求、架構設計、原始碼、測試案例、測試報告、安全分析結果無法證明交付的版本與驗證過的版本是同一份
工具鏈編譯器與其版本、linker script、靜態分析工具與規則集、建置腳本換機器建置就產出不同的 binary，追不出原因
組態設定編譯選項與最佳化等級、RTOS 設定、MPU 區段表、校正參數同一份原始碼在不同設定下行為不同，驗證結果失效
外部元件第三方函式庫、供應商 driver、開源套件與其版本供應商悄悄改版，你的驗證證據跟著失效

可重現性是硬要求，不是最佳實務

組態管理真正的目的是在事故發生後，能把當初出貨的那個版本原封不動重建出來。這不是理想，是責任歸屬的前提：如果三年後有人主張某批車的韌體有問題，你必須能拿出那個版本、重跑分析、證明當時做了哪些驗證。

對韌體團隊的實際意義是：建置要能重現。理想狀況是同一份輸入能產生位元完全相同的 binary，這樣「交付的東西就是驗證過的東西」不需要靠信任，可以直接用雜湊值比對。做不到位元相同時（有些工具鏈會嵌入時間戳或路徑），至少要能明確記錄下所有輸入，並說明差異的來源為何不影響行為。

Change management 的核心邏輯

任何要改動已發布的安全相關產出物，都要先做 impact analysis（影響分析）：這個改動會不會波及已經完成驗證的其他部分？需不需要重新跑哪些測試、重新做哪些安全分析？只有分析完、決定好影響範圍，才能核准變更並執行。

  1. 提出變更請求，說明動機與預期影響範圍。
  2. 進行 impact analysis：對照需求追溯矩陣，找出所有受影響的需求、設計、測試案例。
  3. 核准變更，決定需要重新驗證的項目。
  4. 執行變更、更新受影響的產出物與追溯關係。
  5. 重新驗證，並更新變更紀錄。

影響分析到底在分析什麼

它問的不是「這段程式碼會不會壞」，而是「哪些已經成立的論證，可能因為這個改動而不再成立」。這是完全不同的思考方式，而且要往四個方向追：

  • 往上追需求：這段程式碼實作了哪幾條安全需求？改了之後那些需求還被滿足嗎？
  • 往下追驗證：哪些測試案例涵蓋了這段程式碼？哪些必須重跑？覆蓋率會不會掉？
  • 往旁邊追架構論證：這個改動會不會破壞先前宣稱的獨立性或分區假設？把共同邏輯抽成共用函式，看起來只是重構，卻可能讓兩條原本獨立的路徑產生耦合。
  • 往資源方向追：時間預算、stack 用量、flash 空間有沒有被吃掉？高 ASIL 任務的 WCET 餘裕還夠嗎？

這也是為什麼追溯矩陣不是拿來應付稽核的裝飾品。沒有追溯關係，影響分析就只能靠資深工程師的記憶，而記憶不會在人離職之後留下來。

常見誤解

「只改了一行 log 訊息，應該不用跑 impact analysis 吧」——即使是看似無害的修改，流程上仍然要走過影響分析這一步，差別只在於分析結論可能是「影響範圍極小」。省略分析本身，才是違反流程的地方。

而且「改 log」也未必無害：多一行輸出可能改變時序、增加中斷關閉時間、撐爆 stack，或讓某個函式超過原本量測的 WCET。分析結論通常確實是「影響極小」，但那個結論必須是分析出來的，不是假設出來的。

2驗證與文件化

Part 8 定義了一組跨全生命週期共用的驗證方法：walkthrough（走查）、inspection（正式審查）、以及各種 review。等級越高的 ASIL，對驗證方法的獨立性與嚴謹度要求也越高——例如高 ASIL 的 code review 會要求審查者跟作者不是同一人，甚至要求跨團隊審查。

方法特性常見用途
Walkthrough作者主導講解，較非正式設計早期快速對齊理解
Review有結構、有紀錄，但不一定要求獨立審查者一般 code review
Inspection最正式，要求獨立審查者、明確準則、缺陷紀錄高 ASIL 的關鍵產出物審查

「獨立性」在審查裡指的是什麼

審查的獨立性是有層次的，ASIL 越高要求越往上爬：同一個人自己檢查自己的產出（幾乎不算數）、同團隊的另一個人、不同團隊的人、乃至於不隸屬同一條產品線的獨立單位。背後的道理很簡單——你看不到自己的盲點，而跟你共用同一套假設的同事，往往也看不到。

實務上這會變成很具體的規則：某些關鍵模組的 pull request 不接受同組同事 approve、安全需求的審查必須有安全工程師參與、確認措施（confirmation measures）由專案外的角色執行。覺得綁手綁腳的時候，記得它擋的是「整組人一起看走眼」這種失效模式。

驗證不只是「跑測試」

Part 8 意義下的驗證涵蓋所有產出物，不只程式碼。需求本身要被驗證（是否明確、可驗證、無矛盾）、架構設計要被驗證（是否滿足上層需求）、測試案例本身也要被驗證（是否真的涵蓋需求）。很多缺陷在需求審查階段就能抓到，成本比等到整合測試才發現低了好幾個數量級。

文件化與追溯性

Documentation（文件化）要求每一份產出物都要有明確的目的、讀者、以及跟其他文件的追溯關係。這不是為了製造紙本作業，而是讓稽核者、甚至未來的你自己，能重建「這個決定當初是怎麼做出來的」。

判斷文件夠不夠好有個實用標準：一個沒參與過這個專案的合格工程師，能不能只靠這份文件重現你的推論？如果需要你在旁邊口頭補充才看得懂，那文件就還不合格。這個標準聽起來嚴苛，但想想三年後你自己回來看的處境，就會覺得合理。

3工具信心等級（Confidence in the use of software tools）

這是韌體工程師最常忽略、卻最容易踩雷的一條：你用的編譯器、靜態分析工具、甚至 IDE，理論上都可能因為自身的錯誤而讓不安全的程式碼被誤判為安全。Part 8 用一套流程決定「這個工具需不需要額外做鑑定」。

兩個判斷：工具會不會害到你，以及你抓不抓得到

整套判定只問兩件事。第一個是 TI（Tool Impact）：這個工具如果出錯，有沒有可能在安全相關產品中植入錯誤，或是漏掉本該被偵測到的錯誤？有可能就是 TI1，沒有可能就是 TI2。注意「漏掉錯誤」也算——靜態分析工具不會改你的程式碼，但它漏報一個缺陷，效果跟幫你製造缺陷差不多。

第二個是 TD（Tool error Detection）：對於「這個工具出錯」這件事，你有多少信心能靠其他手段發現？信心高是 TD1、中等是 TD2、其餘一律 TD3。這裡的「其他手段」指的是不依賴該工具本身的檢查，例如編譯器出錯可以靠針對目標硬體執行的測試抓到，因為那是在測最終產出的行為，不是在信任編譯器的宣告。

TD 才是你真正能操作的槓桿

TI 幾乎是工具性質決定的，你改變不了——編譯器就是會產生最終執行的機器碼，它必然是 TI1。但 TD 不同：TD 反映的是你的開發流程有多能抓到工具的錯誤，而流程是你可以設計的。

這帶來一個很實際的策略：與其硬啃工具鑑定，不如強化「不依賴該工具的獨立檢查」。例如針對編譯器，如果你的驗證是在目標硬體上執行編譯後的程式碼、而且測試涵蓋率足夠，那麼編譯器把程式碼編錯的情形有相當機率會在測試中現形，TD 的評等就有依據往上走。反過來說，如果單元測試全部在 PC 上用另一套編譯器跑（host testing），那對目標編譯器的錯誤幾乎沒有偵測力，這一點在評 TD 時會被抓出來。

TCL2 / TCL3 要做什麼

被判到 TCL2 或 TCL3 不代表不能用這個工具，而是要補上「憑什麼信任它」的證據。標準提供幾條可選路徑，依 TCL 與 ASIL 決定建議程度：

鑑定方法實際上在做什麼成本落在哪
使用經驗增加信心
increased confidence from use		拿這個工具版本在類似用途上的既有使用紀錄與問題回報當證據要有紀律地累積並保存紀錄，臨時湊不出來
評估工具開發流程
evaluation of the development process		檢視工具供應商本身是否依合適的流程標準開發這個工具高度依賴供應商配合與提供文件
工具驗證
validation of the software tool		自己準備測試案例驗證工具在你的使用範圍內行為正確要自行設計並維護一套工具測試集
依安全標準開發
development in accordance with a safety standard		工具本身就是照安全標準開發出來的通常是買商用「已鑑定」工具，成本轉為授權費

實務上大多數團隊走的是混合路線：買商用工具鏈時要求供應商提供鑑定套件（qualification kit），自家寫的建置與測試腳本則靠自行驗證。要注意鑑定永遠是「針對特定版本、特定使用範圍」成立的——供應商的鑑定套件通常會附一份使用限制清單，超出清單的用法不在保證範圍內。

為什麼不能隨便升級編譯器版本

如果編譯器被判定為 TCL2 以上，代表團隊曾經針對「這一個版本」做過鑑定措施。換一個新版本，理論上等於換了一個新工具，需要重新評估鑑定是否仍然成立——這也是安全專案往往鎖定特定編譯器版本、不隨便跟進最新版的原因。

同樣的邏輯也適用於最佳化等級與編譯選項。用 -O2 驗證過的結論，不會自動延伸到 -O3；改選項等於改變了工具的使用方式，要重新檢視。這就是為什麼安全專案的建置設定往往被鎖死在版控裡，而不是讓每個人在自己機器上隨手調。

別忘了你自己寫的那些腳本

工具鑑定的討論很容易只聚焦在編譯器和靜態分析器，但團隊自製的東西同樣適用同一套判準：自動產生程式碼的 script、把 Excel 需求表轉成測試案例的轉換工具、計算覆蓋率並判斷是否達標的統計腳本。如果某個腳本會決定「這個模組算不算通過」，而它算錯了又沒有其他檢查抓得到，那它就是 TI1 加上偏低的 TD——實質上比你買的商用工具更需要被檢視，卻常常連版本都沒好好管。

4元件與測試工具鑑定

工具是「幫你做出產品的東西」，元件則是「會被放進產品裡的東西」，兩者的鑑定邏輯相似但要求不同。

Qualification of software components（軟體元件鑑定）：如果你要重用一個既有的軟體元件（例如某個現成的 RTOS、通訊協定堆疊、或第三方函式庫），且這個元件當初不是照 ISO 26262 開發出來的，就需要透過鑑定手段（例如：既有的使用記錄、額外測試、白箱分析）來建立對它的信心，而不能直接假設「大家都在用所以一定沒問題」。

重用一個元件要準備哪些證據

鑑定的核心是把這個元件當成一個有明確契約的黑箱，並證明它在你的使用範圍內守約。實務上通常要湊齊這幾樣：

  • 元件的規格：它宣稱做什麼、介面長什麼樣、有哪些前提與限制。沒有規格就無從驗證——這是很多開源元件卡關的第一關。
  • 使用範圍的界定：你只用到它的哪些功能、在什麼組態下使用。鑑定只在這個範圍內成立，日後要用到新功能就要重新評估。
  • 符合規格的證據：針對你使用範圍的需求導向測試、介面測試、異常輸入下的行為測試。
  • 資源使用的證據：stack 用量、執行時間、記憶體佔用——尤其 RTOS 與通訊堆疊，這些數字直接影響你的時間與記憶體論證。
  • 已知問題清單：供應商的勘誤表與未修正缺陷，以及你打算怎麼迴避它們。

如果選用的是 AUTOSAR 生態裡的商用 BSW，供應商通常會直接提供這整包安全文件，這也是它們定價的一部分。自己從開源專案拉一份程式碼進來，省下的授權費往往會在補這些證據時加倍還回去。

測試工具鑑定

Qualification of software test tools（軟體測試工具鑑定）：邏輯跟工具信心等級類似，但專門針對測試工具本身——如果測試工具本身有問題導致漏掉一個本該被抓到的錯誤，那測試結果就不可信，因此測試工具也需要視情況鑑定。

這裡有個容易忽略的重點：測試工具的錯誤方向是不對稱的。測試工具誤報（把對的判成錯的）會浪費你的時間，但不會傷害安全論證，因為你會去查然後發現是誤報；真正危險的是漏報——測試明明沒真的執行到那段程式碼，覆蓋率報告卻宣稱涵蓋了。這種錯誤會安靜地讓你的證據失真，所以覆蓋率工具往往是團隊裡最需要被檢視的一項。

重用 RTOS / driver需要元件鑑定：使用記錄、額外測試或分析建立信心
換編譯器 / 靜態分析工具版本需要重新檢視 TCL 判定是否仍然成立
自動化測試框架本身需要測試工具鑑定，避免測試結果本身不可信

跟 ASPICE 的關係

很多 OEM 會同時要求 ISO 26262 與 Automotive SPICE，兩者在組態管理、變更管理、追溯性這些主題上高度重疊。差別在於出發點：ASPICE 評的是「你的流程能力成熟度」，ISO 26262 問的是「你能不能論證這個產品夠安全」。實務上一套流程通常同時滿足兩邊的要求，但別把兩者混為一談——ASPICE 拿高分不等於安全論證站得住腳。
