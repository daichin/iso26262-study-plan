總覽

ISO 26262-8 不是「軟體怎麼寫」，而是「整個安全生命週期共用的流程骨架」。這些流程平常感覺像行政作業，但它們存在的理由都很具體：讓每一個決定都能被追溯、讓工具鏈本身不會變成安全的破口。

為什麼軟韌體工程師要懂這部分

Part 6（軟體開發）定義「要做什麼」，Part 8 定義「怎麼做才算數」。你交付的程式碼要進安全案例（safety case），走的就是 Part 8 的組態管理、變更管理與驗證規則。

1組態與變更管理

Configuration management（組態管理）要求每一份會影響安全的產出物——原始碼、需求文件、測試案例、工具版本——都要能被唯一識別、版本化、並且可以重現。這也是為什麼安全專案對「這次建置用的到底是哪個 commit、哪個編譯器版本」要求得比一般專案嚴格得多。

Change management 的核心邏輯

任何要改動已發布的安全相關產出物，都要先做 impact analysis（影響分析）：這個改動會不會波及已經完成驗證的其他部分？需不需要重新跑哪些測試、重新做哪些安全分析？只有分析完、決定好影響範圍，才能核准變更並執行。

  1. 提出變更請求，說明動機與預期影響範圍。
  2. 進行 impact analysis：對照需求追溯矩陣，找出所有受影響的需求、設計、測試案例。
  3. 核准變更，決定需要重新驗證的項目。
  4. 執行變更、更新受影響的產出物與追溯關係。
  5. 重新驗證，並更新變更紀錄。

常見誤解

「只改了一行 log 訊息，應該不用跑 impact analysis 吧」——即使是看似無害的修改，流程上仍然要走過影響分析這一步，差別只在於分析結論可能是「影響範圍極小」。省略分析本身，才是違反流程的地方。

2驗證與文件化

Part 8 定義了一組跨全生命週期共用的驗證方法：walkthrough（走查）、inspection（正式審查）、以及各種 review。等級越高的 ASIL，對驗證方法的獨立性與嚴謹度要求也越高——例如高 ASIL 的 code review 會要求審查者跟作者不是同一人，甚至要求跨團隊審查。

方法特性常見用途
Walkthrough作者主導講解，較非正式設計早期快速對齊理解
Review有結構、有紀錄，但不一定要求獨立審查者一般 code review
Inspection最正式，要求獨立審查者、明確準則、缺陷紀錄高 ASIL 的關鍵產出物審查

Documentation（文件化）要求每一份產出物都要有明確的目的、讀者、以及跟其他文件的追溯關係。這不是為了製造紙本作業，而是讓稽核者、甚至未來的你自己，能重建「這個決定當初是怎麼做出來的」。

3工具信心等級（Confidence in the use of software tools）

這是韌體工程師最常忽略、卻最容易踩雷的一條：你用的編譯器、靜態分析工具、甚至 IDE，理論上都可能因為自身的錯誤而讓不安全的程式碼被誤判為安全。Part 8 用一套流程決定「這個工具需不需要額外做鑑定」。

為什麼不能隨便升級編譯器版本

如果編譯器被判定為 TCL2 以上，代表團隊曾經針對「這一個版本」做過鑑定措施。換一個新版本，理論上等於換了一個新工具，需要重新評估鑑定是否仍然成立——這也是安全專案往往鎖定特定編譯器版本、不隨便跟進最新版的原因。

4元件與測試工具鑑定

Qualification of software components（軟體元件鑑定）：如果你要重用一個既有的軟體元件（例如某個現成的 RTOS、通訊協定堆疊、或第三方函式庫），且這個元件當初不是照 ISO 26262 開發出來的，就需要透過鑑定手段（例如：既有的使用記錄、額外測試、白箱分析）來建立對它的信心，而不能直接假設「大家都在用所以一定沒問題」。

Qualification of software test tools（軟體測試工具鑑定）：邏輯跟工具信心等級類似，但專門針對測試工具本身——如果測試工具本身有問題導致漏掉一個本該被抓到的錯誤，那測試結果就不可信，因此測試工具也需要視情況鑑定。

重用 RTOS / driver需要元件鑑定：使用記錄、額外測試或分析建立信心
換編譯器 / 靜態分析工具版本需要重新檢視 TCL 判定是否仍然成立
自動化測試框架本身需要測試工具鑑定，避免測試結果本身不可信

測驗：你讀懂了多少？
